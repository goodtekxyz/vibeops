### 결정 요약

- VibeOps는 코드를 생성하지 않는다(Cursor가 생성). VibeOps는 부트스트랩 + TASK 라이프사이클 + Notion 동기화 “레일”이다.
- Source of Truth는 Git의 `docs/tasks/*.md`와 `docs/project/*.md`. Notion은 사람이 보는 대시보드이고 메타만 동기화.
- 모든 변경 명령은 가능한 `--dry-run`을 제공.
- `init`은 idempotent, 기본은 덮어쓰지 않음(`--force` 필요).
- `task rollback`은 안내가 기본, 파괴적 작업은 `--confirm` 필요.

## TASK-006 · `vibeops plan` 구현 완료

20문항 대화형 흐름으로 ProjectBrief markdown과 Cursor Planner 프롬프트를 생성하는 본체를 구현했다. 사용자 재확정 스펙(`.vibeops/brief/project-brief.md` + `.vibeops/generated/plan-prompt.md`, 필드 이름 `mvpFeatures / dbLayer / integrations / useNotion / useGitWorkflow / risks`, useNotion 기본 true, agentWorkflowLevel 기본 Advanced)을 기준으로 구현.

### 핵심 결정

- **brief 직렬화는 markdown**: JSON 후보를 버리고, 사람이 직접 검토·편집하기 쉬운 markdown으로 떨어뜨린다. `## N. <title>` 헤딩 + 값(스칼라/리스트/yes·no) + 끝에 `## Assumptions`. 헤더에 `Generated · vibeopsVersion · Source · schemaVersion`.
- **`--apply / --resume`은 본 TASK 비스코프**: 사용자 스펙이 brief + planning prompt 생성까지로 한정. 분배는 별도 TASK 후보로 남김.
- **Other 체인**: select/checkbox에서 `Other` 선택 → follow-up `input`. 빈 입력은 `"Other"` 유지, 텍스트 입력은 `"Other: <text>"`. checkbox는 콤마 분리로 여러 개 입력 가능.
- **non-TTY guard**: 파이프/CI에서 인터랙티브 진입 시 한 줄 안내 후 exit 1. `--non-interactive` 또는 `--from <path>` 사용 강제.
- **`--idea "Name: idea"` 분리 휴리스틱**: 콜론 앞이 한 단어이고 40자 미만이면 projectName + oneLineIdea로 자동 분리(BYOBrowser 예시 동작).
- **`@inquirer/prompts 8.4.3`** 채택. checkbox는 v8에서 `instructions` 옵션이 사라져서 안내 텍스트를 message 자체에 dim ANSI로 인라인.
- **stdout/stderr 정렬**: 초기 구현에서 `log.warn`(stderr) ↔ `log.info`(stdout) 인터리브로 “Assumptions” 헤더가 다음 단계 사이에 끼는 버그 발견 → 모두 stdout으로 통일.

## TASK-006 · `vibeops plan` UX 개선 라운드

대화형 흐름의 사용성 문제 3가지를 정리: 선택지가 너무 많아 스크롤이 길고, 기본값이 선호 스택과 어긋나며, select·checkbox가 끝에서 처음으로 점프하는 루프가 거슬렸다. 모두 본 라운드에서 해결.

### 핵심 결정

- **선택지 다이어트**: 12개 카테고리에서 합계 24개 항목 제거. 합계 116 → 92. `Other`는 모든 카테고리에서 **항상 마지막** 위치(자주 안 보이게).
  - Project type: `Chrome Extension / API Service / Content Site` 제거
  - Target users: `Creators / Agencies / Enterprise users / Consumers` 제거
  - MVP must-have features: `User settings / Notifications / Billing / Admin panel / API endpoints / File upload` 제거
  - Out of scope: `Multi-language / Chrome extension` 제거
  - Frontend: `SvelteKit / Vue/Nuxt` 제거, `Other` 추가
  - Backend: `Node.js Express / None / frontend only` 제거(→ `None` 단순화), `Other` 추가
  - Database: `MongoDB` 제거, `Other` 추가
  - DB Layer: `Supabase client` 제거, `Other` 추가
  - Deployment target: `GCP / Azure / Railway / Render` 제거, `Other` 추가
  - Auth requirement: `Passkey` 제거, `Other` 추가
  - External integrations: `Google Calendar / Discord` 제거, `Other`를 `None` 뒤로 이동
  - Risk areas: `Legal/compliance / Payment/billing` 제거
- **기본 스택 디폴트**: `frontend=Next.js`, `backend=NestJS`, `database=PostgreSQL`, `dbLayer=Drizzle`, `packageManager=pnpm`. 모두 신규 선택지 목록의 첫 번째 항목.

## TASK-008 + TASK-009 · MVP 3 Git Task Lifecycle 구현 (Review 대기)

VibeOps의 "레일" 본체. `task start / prompt / check / done / rollback`을 모두 본체 구현. 사용자의 갱신된 요구를 따라 Status 흐름은 **Planned → In Progress → Review → Done** 4단계로, Git 상태는 별도 JSON 대신 TASK markdown의 **`## Git Context`** 섹션에 inline 기록한다.

### 핵심 결정

- **Status 4단계.** `src/types/task.ts`에 `"review"`를 추가. `task done` 기본은 `Review`로 두고, 사람이 검토 후 `--finalize`로 `Done`까지 보낸다. 자동 commit · 머지 · 푸시는 어떤 경로로도 발생하지 않는다.

## TASK-008 후속 패치 · `task check`의 changed-files 감지 확장

### 문제

`vibeops task check TASK-008` 출력에서 Git status는 `dirty`인데 `changed files 0`이 표시되던 버그. 원래 로직이 `git diff --name-only baseCommit..HEAD` 만 보고 있어 working tree에 있는 unstaged / staged / untracked 파일을 전혀 포함하지 못했다. 결과적으로 `Expected Files to Change` 매칭도 항상 0%로 표시되어 reviewer가 진행 상황을 가늠할 수 없었다.

### 핵심 결정 (TASK-008 범위 내)

- **합산 정책**: `task check`는 4 카테고리를 모두 본다 — unstaged, staged, untracked, committed(`baseCommit..HEAD`). Set-dedup으로 중복 제거.
- **출력 분해**: 기존 `changed files <n>` 한 줄을 다음 3줄로 교체.
  ```
  working tree changed files <n>   ← unstaged + staged + untracked의 union
  committed changed files <n>      ← baseCommit..HEAD의 변경 파일
  total changed files <n>          ← working tree ∪ committed의 union
  ```
- **Expected Files 매칭 기준**: 이제 `total` 기준. 매칭 결과 뒤에 `basis: working tree(N) ∪ committed(M) = total(K) files`를 출력해 합산 근거를 명시.
- **`git status --porcelain` 파서**: `src/lib/git.ts`에 `parsePorcelainLine`을 둬서 XY 상태 코드(2자) + 공백 + 경로를 분리. `??`는 untracked, `R  old -> new` / `C  old -> new`는 새 경로(`new`)를 changed file로 잡는다. `!!`(ignored)는 무시.
- **read-only 강제**: 새 헬퍼는 모두 비-throw read 래퍼(`tryGit`) 위에서 동작. mutating `runGit`은 호출하지 않는다. `task check` 자체도 `writeText` / `gitCheckout` / `updateInlineStatus` / `upsertGitContext` 등 어떤 mutating 호출도 하지 않음(코드 grep으로 재확인).

## TASK-010 후속 UX 패치 · `notion init` Yes/No → select 통일

### 결정

  ```ts

    // select<boolean> · choices [{name:"Yes",value:true},{name:"No",value:false}] · loop:false · pageSize:2
  ```

- token 입력은 `@inquirer/prompts` 의 `password({ mask: "*" })` 로 받는다 — 입력값이 화면에 표시되지 않음.
- 보안 정책 갱신: `.vibeops.env` 는 기본적으로 자동 생성하지 않는다. 단, interactive setup 에서 사용자가 `Paste NOTION_TOKEN now? = Yes` 를 명시적으로 선택한 경우에만 생성/업데이트한다. `dry-run` / `non-interactive` / `No` 선택 / 비-TTY 경로에서는 만들지 않는다.

### 결정

- 사용자 갱신 요구에 따라 동기화 표면을 다음 둘로만 한정한다.
  - **`vibeops notion sync`** — `docs/project/{00-overview,05-current-state(또는 03)}` + `docs/tasks/*.md` 의 메타 → Projects DB 1 행 + Tasks DB N 행 upsert. `Project ID` (Projects) / `(Project ID, Task ID)` (Tasks) 가 매칭 키.
  - **`vibeops task pull`** — Notion Tasks DB 에서 `Project ID == config.name AND Status ∈ {Planned}` (또는 `--status` 로 지정) 인 행을 query → 로컬에 없는 TASK 만 18-섹션 skeleton 으로 생성 + 빈 `Docs Path` 만 한 줄 역방향 update.
- `--dry-run` 의 의미: `databases.query` 까지는 허용 (existing page 매칭 분석용), `pages.create` / `pages.update` 는 도달 자체를 막는다. 명령 본체의 분기에서 `dryRun === true` 면 mutation 호출 라인 이전에 일찍 return.
- Notion property 매핑은 schema-driven — Projects DB 의 `Git Repo` 가 `rich_text` 인지 `url` 인지 `databases.retrieve` 시점에 감지해서 `buildProjectProperties(project, gitRepoType)` 가 그에 맞춰 분기. TASK-010 의 `notion-schema.ts` 가 이미 두 타입을 허용하도록 정의돼 있어 재사용.

## TASK-010 follow-up #3 · Notion discovery 버그 수정 (object filter `data_source`)

### 요약

Yes" 흐름에서 Notion REST API 가 `validation_error: body.filter.value should be \`"page"\` or \`"data_source"\`, instead was "database"` 를 돌려주던 버그를 수정했다. 현재 Notion API 는 `POST /v1/search` 의 `filter.value` 로 **`page` 또는 `data_source` 만** 받는다. 과거의 `"database"` 는 영구 폐기.

### 결정

- 검색은 항상 `objectFilter: "data_source"` 로 호출한다. `database` 리터럴은 SDK 호출 인자로 더 이상 송신하지 않는다.

- 응답 normalize 는 `database` / `data_source` 두 종류 모두 받아들인다 (Notion 측에서 양 형태가 혼재 가능).
